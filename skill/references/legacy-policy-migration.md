# Preserve an existing project's operating contract

Use only when updating an existing C2C instruction installation. New adopters with an adequate task contract do not need this legacy policy or any companion method. This is a one-time maintenance procedure, not a new runtime, policy package, approval phase or universal dependency.

## Separate transport from continuing project duties

C2C now owns connection, authorized message delivery and checkpoint continuation. The existing Project/boot instruction owner retains the operating decisions already adopted for that project. Updating transport does not waive writer or exception authority, approvals, investigation/review duties, record format, privacy, loop limits or unfinished obligations. No private account plugin is needed.

The following bundled public files remain frozen 0.3.3 compatibility sources, not policy selected for every new C2C task:
- [collaboration-policy.md](collaboration-policy.md)
- [full-format.md](full-format.md), record format 1.0.1
- [approved-source.json](approved-source.json), which binds those full-format bytes, not a new transport release

The existing repository maintainer remains responsible for these frozen compatibility resources; future changes require explicit compatibility review. This creates no new authority or package.

Their reviewed public baseline is commit [e820ec5b038311e0ab6f74ef14fb18b89bb6846e](https://github.com/jack61714z/codex-with-chatgpt/tree/e820ec5b038311e0ab6f74ef14fb18b89bb6846e). Legacy full-format SHA-256 is 82b866499d13f27487a46a63b5e38fa3ac5f4b11b855a0b71a8b955eeaed401c (13,197 UTF-8 bytes). Preserve actual local customizations and the selected version, which may differ. Do not substitute another deployment's policy merely because it has a newer version.

## Before replacing an existing entry

1. Read its actual Project/boot instructions, selected policy/record source and local overlays. Save the previous source and installed recovery copy under the existing maintenance procedure. Identify the existing responsible owner; do not invent a new actor or infer permission from tool availability.
2. In the existing authorized Project/boot instruction location, retain the selected operating contract and the legacy loop rule below. A preserved local source, existing bundled compatibility source or accessible commit-pinned source is sufficient; verify required references resolve. No new repository, tracker or plugin is required.
3. Add an explicit source selection in those existing instructions, using actual verified locations: “For this existing project, retain the operating contract selected before the transport update, including writer/exception authority, approvals, investigation/review duties, record format, loop limits and evidence restrictions. Source: [verified preserved or pinned source plus actual overlays]. These are this project's continuing duties; C2C carries messages and checkpoint state only.” The placeholder must be filled before claiming selection. Carry the full applicable content where a locator cannot be read.
4. Read back that selection and the preserved applicable contents before replacing the transport entry. If ownership, required content or source loading is unresolved, retain that consumer's previous usable instruction set and report the exact gap. Do not block unrelated work, invent approval or remove a duty by silence.
5. Apply only the authorized instruction update at a safe checkpoint. Preserve task/workspace, iteration, actual executor, candidate, completed work, sent/unsent status and still-valid effect approvals. Verify the fresh reader loads transport and its selected project contract. Saved source, installed files, loaded instructions, decisions and operational delivery are separate claims. Never re-pair, reset, resend or reexecute completed work to demonstrate the change.

The current installer copies incoming text and preserves extra destination text files. It neither chooses operating policy nor deletes retired files or updates Projects. Deleting a repository file is not evidence that installed consumers stopped reading it. Keep frozen compatibility sources available until their actual consumers have a supported alternative. This does not make the legacy policy mandatory for new users.

## Legacy 0.3.3 loop rule retained by the project

This paragraph is the original rule from the old protocol. Retain it as project policy for existing adopters unless their actual authorized instructions already select a different rule. Do not impose it as a new transport default on all users.

Read `maxIterations` from the workspace's `.c2c.json`; when absent, use the workflow default of 12 iterations for a fresh installation. The CLI parses this setting but does not enforce the loop limit at runtime; the assigned writer checks the current checkpoint iteration before starting another iteration. An invalid configured limit goes to Chat for assessment rather than silently changing configuration. At the limit, pause further implementation and return progress, unresolved issues and loop evidence to Chat for a progress/loop assessment. Chat decides scoped continuation or a changed strategy within existing authority; this is not a new user signature for routine continuation. The limit does not authorize changing unrelated configuration or continuing an explicit stop. New scope/destructive/disclosure/consent and merge boundaries go through Chat to the user.

## Legacy payload and authority remain unchanged

An existing project retaining 1.0.1 keeps its Chat-only literal completion question, full seven-axis review, nullable planning head, unknown actual executor, separate numeric iteration/repair label, evidence limitations and authorized record persistence. It retains the public policy's daily writer with explicit bounded user exceptions and an explicitly assigned merge executor under exact-head approval. New transport simply carries those payloads. No other deployment's completion literal or private policy is imported.

Keep historical records under their original source/format; do not rewrite or resend them to adopt transport wording. Selecting an optional work-record template does not remove required fields or semantic duties. Each of goal alignment, closure improvement, tracking and templates may be selected independently by its own authorized project; none is a prerequisite of C2C or of another method.

## Verification and recovery

Check a normal authorized delivery and a retained project-policy restriction: transport must not require an unrelated method, while the selected policy must still prevent an unauthorized action. Confirm EXECUTED_LOCAL sends only unsent work and EXECUTED_SENT does not repeat execution or delivery. Preserve existing browser, Doctor, credential, denial and platform restrictions.

If the changed reader cannot resolve its selected contract, restore its prior usable instruction selection at a permitted checkpoint, preserving current effects and history. Do not overwrite later local edits or infer that restoring text undoes an external effect. No all-session activation or efficacy is established by this procedure alone.
